[#PermissionRules]
== Permission Rules
include::../variables.adoc[]

QPermissionRules controls access to metadata objects such as tables and processes. Authentication identifies a session; permission rules determine which operations that session may perform. Instance defaults and object-specific rules are combined by PermissionsHelper. Configure and test both allowed and denied operations rather than treating a visible menu item as an authorization check.

=== QPermissionRules

* `level` selects `NOT_PROTECTED`, `HAS_ACCESS_PERMISSION`, `READ_WRITE_PERMISSIONS`, or `READ_INSERT_EDIT_DELETE_PERMISSIONS`.
* `denyBehavior` is `HIDDEN` or `DISABLED` for presentation of denied metadata.
* `permissionBaseName` customizes the base used to construct permission names.
* `customPermissionChecker` references an implementation of CustomPermissionChecker for application-specific checks.

[source,java]
.An object rule requiring separate read/insert/edit/delete permissions
----
QPermissionRules rules = new QPermissionRules()
   .withLevel(PermissionLevel.READ_INSERT_EDIT_DELETE_PERMISSIONS)
   .withDenyBehavior(DenyBehavior.HIDDEN);
----

Attach the rule to the relevant metadata object and supply the matching permissions in the session. QPermissionRules.defaultInstance() uses NOT_PROTECTED and HIDDEN; it is not a secure application-wide policy by itself. Record-level security keys are a separate part of access control.

=== Joined HTTP reads

The legacy and V1 Query/Count endpoints require READ for the base table and every table requested through joins, qualified filter fields or ordering. Aliases and intermediate tables in a join path do not bypass this check. Legacy Get applies the same rule to requested joins and associated-record expansion, including nested associations. Making a join exposed or granting WRITE does not grant READ. Denied requests return HTTP 403 without records or counts. A join added solely to enforce a record-security lock remains internal to that enforcement; a client who also requests its data must have READ permission.

These checks apply at the HTTP boundary. Trusted core actions still support internal application operations without automatically requiring the public endpoint's table grants. This distinction does not replace authentication or record-level security.

HTTP Query/Count inputs use `QInputSource.USER`, and associated-record queries inherit their parent's input source. A personalizer that removes fields for USER reads therefore applies to associated children and grandchildren as well. Association authorization follows the personalized association metadata; removed associations are not expanded.

If personalization fails while validating a joined filter field, the filter is rejected. An error must not restore the table's unrestricted field definitions.
