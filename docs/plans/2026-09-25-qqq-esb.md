# QQQ ESB Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Each task below is one GitHub issue and one PR. Work test-first: write the listed tests, watch them fail, implement, watch them pass, commit. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Queues and topics for QQQ tables and processes over JMS (ActiveMQ Artemis, RabbitMQ), with permission-scoped observability and management in qqq-frontend-next, shipped in qqq 4.1.

**Architecture:** Three small no-op hooks in `qqq-backend-core`; everything else in a new `qqq-esb` module that registers against those hooks, runs JMS consumers, and serves `/qqq/v1/esb` endpoints; Next renders the ESB app and Developer-view sections from those endpoints.

**Tech Stack:** Java 21, Jakarta Messaging 3.1 API, ActiveMQ Artemis Jakarta client, RabbitMQ JMS client 3.9.0, Javalin (via `qqq-middleware-javalin`), JUnit 5, embedded Artemis, Testcontainers 2.0.3; Next.js + TypeScript, Vitest, Playwright.

**Spec:** `docs/specs/2026-09-25-qqq-esb-design.md` (approved 2026-09-25, amended same day: broker-redelivery retries, Classic dropped, unique subscription names).

## Review Focus

1. **Bulk write:** inserting 5,000 records into a publishing table publishes 5,000 messages after commit on one reused session; the insert succeeds. → Task 8 test `bulkInsertPublishesAllAfterCommit`.
2. **Broker down on save:** the record save succeeds within the 5 s connect timeout, and the failure is counted, not thrown. → Task 8 test `saveSucceedsWhenBrokerDown`.
3. **Poison message:** a non-JSON or non-CloudEvent message on a trigger's queue goes straight to the dead-letter queue with `qqqError = "unparseable message"`, without retries. → Task 10 test `unparseableMessageDeadLettersImmediately`.
4. **Shutdown mid-run:** stopping the runtime during a slow run rolls the message back, and it is processed after restart, not lost. → Task 10 test `stopDuringRunRedeliversAfterRestart`.
5. **Self-trigger loop:** a process triggered by table X that updates table X produces events whose CloudEvent `qqqcausationid` equals the triggering event's `id`. There's no automatic suppression in 4.1; this is documented. → Task 10 test `triggeredWritesCarryCausationId`.

### Task 10: Trigger runtime (`qqq`)

**Files:** Create in `qqq-esb/.../runtime/`: `QEsbRuntime.java`, `EsbTriggerRunner.java`, `EsbTriggerHandler.java`, `EsbTriggerState.java`. Test: `EsbQueueTriggerTest`, `EsbTopicTriggerTest`, `EsbRetryAndDeadLetterTest`, `EsbBatchTriggerTest`.

**Consumes:** Tasks 5, 6. **Produces:**
```java
QEsbRuntime.start(QInstance) / stop() / isRunning()
QEsbRuntime.getRunner(String triggerName): EsbTriggerRunner
EsbTriggerRunner.getState(): EsbTriggerState      // RUNNING, PAUSED, CONNECTING, STOPPED
EsbTriggerRunner.pauseLocal() / resumeLocal() / restartLocal()
EsbTriggerHandler.runProcess(EsbTrigger, String processName, List<EsbEvent>) throws Exception   // used by Task 15 replay
```
- **Consumers:** each runner starts `concurrency` virtual threads, each with a transacted session and a consumer. Queues use `createConsumer`; topics use `createSharedDurableConsumer(topic, effectiveSubscriptionName)`. Receive loop timeout is 1 s.
- **Run context:** each run does `QContext.init(qInstance, runAsSessionSupplier.get())`, with `QSystemUserSession` as the default. It runs the process with `FrontendStepBehavior.SKIP` and value `esbMessages` = `ArrayList<EsbEvent>`. When the event's table equals the process's `tableName`, it also sets a `QProcessCallback` filter `primaryKey IN (subjects)`.
- **Causation:** `EsbCausation.set(event.id)` during the run.
- **Retries:** use spec §6, amended, with `JMSXDeliveryCount` as the attempt number. Unparseable messages dead-letter immediately. On timeout the run thread is interrupted and the run counts as failed.
- Call the one-argument `getEffectiveDeadLetterDestinationName` only after `QContext.init` (it reads the instance from `QContext`), or use the two-argument overload.
- **Dead letters:** go to `effectiveDeadLetterDestinationName` with properties `qqqError`, `qqqFailedTrigger`, `qqqAttempts`, `qqqFailedAt`.
- **Batch mode:** collect up to `batchSize` messages or wait up to `batchWaitMs`, then run once and commit or roll back together.
- **Startup and reconnect:** `start` never blocks; runners wait in `CONNECTING` and rebuild after reconnect. `startPaused` applies.

- [ ] Tests: queue trigger runs once per message; concurrency 3 runs 3 in parallel; topic trigger in two runtimes on one broker: each message processed once; message sent while the runtime was stopped is processed after start; fail twice then succeed with `maxAttempts=3`; always fail → one dead letter with the four properties; `DISCARD` drops it; backoff 200 ms delays the retry ≥ 200 ms; batch of 10 in one run; `unparseableMessageDeadLettersImmediately`; `stopDuringRunRedeliversAfterRestart`; `triggeredWritesCarryCausationId`; run-as session without process permission → dead-lettered with a permission error; table-bound process receives the callback filter.
