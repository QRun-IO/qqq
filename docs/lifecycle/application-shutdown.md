# Application shutdown and final resource cleanup

`QApplicationLauncher.stop()` retains reverse startup order: runtime services, the scheduler when present, then HTTP. Once it has attempted every stop, it invokes `QRuntimeServiceInterface.afterApplicationStop()` for successfully started runtime services in reverse order. The default callback does nothing, so existing services need no changes. Ordinary exceptions and linkage errors in a stopper or final callback are logged without skipping the remaining callbacks. Startup failure also cleans up previously started services; a service whose `start()` threw remains responsible for its own partial resources. Repeated completed launcher stops do nothing. Same-thread `stop()` calls from either shutdown phase return immediately; other threads remain serialized until the active stop returns. The in-progress guard is local to each launcher and resets even when an error escapes the existing catch policy, allowing a later cleanup retry. Such an interrupted attempt can repeat callbacks on retry. `run()` creates a separate launcher; there is no public restart operation on an existing launcher. Final callbacks must not assume a `QContext` is available.

ESB stops consumers in `EsbRuntimeService.stop()` and releases provider connections only in the final callback. This preserves already borrowed publishing sessions and permits application work to publish while scheduler or HTTP work finishes. Direct runtime-service callers must invoke `afterApplicationStop()` after their application producers have stopped; `stop()` alone is no longer final provider cleanup. Independent `QEsbRuntime.stop()` still leaves publishing usable, and `EsbConnectionManager.closeAll()` remains a reusable reset. No shutdown order or timeout changes: notably, the Simple scheduler still waits up to 300 seconds. A final callback runs after stop attempts, not a guarantee that failed or timed-out services have drained; noncooperative work can still publish later. There is no forced termination or permanent publishing prohibition. Native regressions cover a scheduled completion, an HTTP process request held across ESB stop, and a real publisher held after its first native transacted send. Exact events commit and arrive, and client provider cleanup completes before launcher return. Broker-side connection counts use the existing bounded observation after return, before any fixture cleanup. The HTTP case uses a scheduled guard and does not claim a new HTTP graceful-drain guarantee.
