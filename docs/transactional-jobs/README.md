# Transactional record-to-Job enlistment (candidate)

This candidate uses the existing Jobs tables as the durable intent. It is not a second outbox or scheduler. It has not been installed into shared artifacts. Enabled-provider qualification is in progress; the ordinary POST hook remains synchronous and does not attest that its caller committed.

A host declares `TransactionalRecordChangeMetaData` on a source table before installing its required listener. The native insert/update/delete action then owns or joins one qualified transaction over the entire operation, including associated writes. Missing/broken required listeners and caught required failures poison that transaction. A caller cannot catch such a failure and subsequently commit it. Unmarked tables retain their existing behavior.

Inside the exact active required event, trusted Java host code calls:

```java
DurableJobs.enlistFixedProcess(event,
   new FixedProcessRequest("declaredProcess", serverOperationKey, dispatchValues));
```

The operation key identifies this logical mutation attempt, not merely a primary key. `TransactionalRecordChangeScope.admittedEvent(event).eventId()` is generated once per exact active native event and remains stable across repeated queries/enlistment calls in that event. Later identical mutations receive different event IDs. A consumer can derive its key from event ID, binding and record ordinal without another registry. This identity does not supply cross-request exactly-once behavior; a host retry across native invocations still needs its own stable operation contract. It must remain stable when the host retries the same mutation. The source event itself is bounded and fingerprinted; an equivalent fabricated event or a delayed callback is rejected. Source values contribute to the fingerprint but are not automatically persisted as job parameters. The host must explicitly authorize any retained dispatch inputs. The returned job ID remains provisional until the source transaction commits.

The source write, job, one chunk, signed initiating-user grant and required launch event share the exact connection and transaction. Workers cannot see those rows before commit. Rollback removes all of them. Worker polling discovers committed work after a crash without requiring an in-memory commit callback. External effects remain subject to the existing Jobs lease, fencing and `NONE` replay policy; uncertain execution requires review rather than claiming exactly-once delivery.

Replacing the Jobs grant key invalidates prior grants and prior keyed fingerprints. Drain or reconcile existing work before rotation. A same-operation retry after rotation finds its old dedupe key and fails closed on the changed fingerprint; it never creates a replacement job or rebinds the old grant. Deliberately new work needs a new server operation identity after the host resolves the prior outcome. No keyring, hidden secret or automatic migration is introduced.

The first fixed-enlistment path requires an interactive initiating identity that can receive the existing signed Jobs grant. Access-token/scoped-credential and service-principal initiators are explicitly refused. The worker must reconstruct current authority using that grant; an enlisted row with a missing grant cannot use the legacy automated-user fallback. A future service-principal adapter needs an explicit reviewed identity contract. No synthetic system actor is used to run user work.

## Host configuration and schema

Before deploying this core metadata to **any existing Jobs host**, apply the three nullable-column additions, even when transactional admission stays disabled. Native queries otherwise select missing columns. Old rows may leave those values null. Apply the guard/schema qualification before enabling `DurableJobsMetaData.withTransactionalAdmissionEnabled(true)` on **all writers sharing the database**; mixed old/strict writer deployments do not provide the shared capacity invariant. Fixed enlistment additionally requires a stable `withTransactionalNamespace("application-id")`. Namespace/backend/actor/source event/process/operation form the dedupe key. Captured security scope, parameters, event fingerprint and host process revision form a domain-separated HMAC intent fingerprint using the existing Jobs grant key. Public metadata never stores the raw record-event SHA; the package-private primitive is not exposed to scripts or an API. The stable dedupe key is independent of secret key material. A retry reauthorizes and rejects a changed fingerprint, including changed scope; mutable display names are not new dedupe identities.

The host process explicitly declares `DurableProcessMetaData.withTransactionalRevision("release-id")`. Only a bounded linear list of fixed Java backend steps is admitted. The worker rechecks that revision before execution. Hosts must change the revision when the implementation changes; this is a host release contract, not automatic bytecode attestation. A script adapter must separately pin and verify its published script build and recheck current binding policy. That adapter is not included in this tranche. A dispatcher calls `DurableJobs.requireEnlistedExecution(processName, revision)` inside its native worker chunk and uses its immutable persisted parameters, not process input supplied by a caller. Only the native runtime installs this scope after initiating-session restoration. Direct and ordinary process launches cannot satisfy it. The check revalidates the current actor, process, signed grant and live database lease, and may be repeated before and after external worker execution. It does not replace application source/binding permissions or guarantee an external effect remains atomic after a lease check.

Jobs-owned tables use the standard snake_case mapping. The supplied additive migrations preserve old nullable job rows. Existing PostgreSQL Jobs hosts also need equivalent nullable `enlistment_key VARCHAR(64)`, `intent_fingerprint VARCHAR(64)` and `process_revision VARCHAR(128)` columns plus the nullable unique enlistment key before adopting this metadata; native PostgreSQL qualification is described below. No production PostgreSQL or qbit-jobs source was changed.

Baseline Jobs tables must already exist with their complete owner schema and indexes; runtime admission does not create or migrate tables. MySQL identity columns require `utf8mb4_0900_bin`. Jobs DATE_TIME columns must use the native zone-less SQL TIMESTAMP/DATETIME convention; timezone-bearing H2 columns are refused because native UTC wall-clock binding would shift them on non-UTC hosts. A trusted migration authority owns DDL and storage configuration; runtime probes do not protect against a hostile database administrator or a dishonest disk.

Qualification uses the actual writable source connection, not merely its configured vendor: same backend/database, READ COMMITTED, native transaction-participating tables, expected owner mappings/types/keys, synchronous file H2 or MySQL 8.4 durability settings, and bounded statement/row/metadata locks. A pre-seeded `jobs_admission` row is locked before budget reads and changes. There is no pooled-session mutation or separate connection for the enlisted intent. MySQL requires recovering doublewrite, flush-on-commit, synchronized binary log when enabled, UTC session and bounded lock waits. Other vendors and in-memory H2 refuse strict admission. Provider qualification remains an execution gate, not a claim from source inspection alone.

## Native PostgreSQL 17 (native postgres backend)

Qualified for the native QQQ postgres module only: vendor and backend type must both be `postgres` (a `postgres` vendor label on the generic rdbms type is refused). The source connection must be the same server URL, database and schema as the configured backend on a writable PostgreSQL 17 primary. Every participating table (source, the four Jobs tables and `jobs_admission`) is resolved the way the next unqualified statement resolves it and must be a permanent (logged), ordinary, non-partition table in the current schema, so temporary, unlogged, foreign, view, partitioned and partition tables are refused; the application role must be data-manipulation only (no superuser, createrole, createdb, replication or bypassrls), must equal the session user, and must not own any of these tables. Session settings must be READ COMMITTED, UTC, `fsync` and `full_page_writes` on, `synchronous_commit` on or remote_apply, and a `lock_timeout` of 1 to 5000 ms (set them at the role or pool level; the JVM zone must be UTC because the driver announces it). Primary and unique keys are read from valid, non-partial, non-expression indexes; text columns must use deterministic collations. DATE_TIME columns may be `timestamptz` or `timestamp` under the enforced UTC session. `postgres-additive.sql` is the trusted migration for old Jobs rows. Evidence: `PostgresTransactionalJobsTest` runs every inherited native Insert/Update/Delete hook, durable-admission, rollback, exactly-once and capacity case on a real server, plus the refusals above (opt-in: `-DpostgresTransactionalJobsTests=true`, Docker required).

## Capacity and control

Enable strict mode at a quiescent, reconciled rollout point. Existing counted rows must use canonical lowercase channel names (suffixes retain their original content), and non-executing jobs cannot retain RUNNING chunks. Runtime admission rejects inconsistent legacy rows; reconcile them under the old supported control path before enablement. The opt-in shared admission lock covers inserts and positive membership changes to waiting, assistant-active and execution-active budgets. Resume, retry, restart, effect-review recovery, owner/process changes and inline tracking cannot bypass those budgets. Execution-active job counts include inline rows in strict mode. Already-running external inline work cannot be retroactively bounded; refusal only denies tracking. Strict `runAgain` reserves before starting asynchronous work.

Controls bind chunk changes, job state and required events to one transaction. Admission comes first, then existing chunks before the job row to match progress-writer order. A failed reservation leaves chunks, state and grants unchanged. Claimers recheck complete current user/process job counts and per-job running chunk counts under the guard. Job-level budgets and chunk parallelism are separate; an idempotent self-transition does not reserve twice. Disabled mode retains existing scheduling semantics **after the additive columns are deployed**. Waiting/paused cancellation with no running chunks completes directly, without consuming an execution slot. Retry/resume retain RUNNING membership while chunks still run.

The shared row deliberately serializes admissions. A source transaction should be short; bounded lock refusal provides backpressure. Qualification cost and contention need measurement on the target provider. No fixed throughput or production capacity is asserted.
