= OAuth2 refresh tokens

`OAuth2AuthenticationModule` can keep a user's session alive after its access token expires. If the provider returns a refresh token at login, QQQ stores it on the server. When the access token expires, or is about to, QQQ uses the refresh token to get a new one, so the user doesn't have to log in again through the identity provider. Without this, a session ends when its first access token expires.

== Enabling it

. *Ask for a refresh token.* Most providers issue one only when the `offline_access` scope is requested and allowed for the client. Next UI 1.0 requests `offline_access` by default. Add it to the OAuth2 meta-data `scopes` as well, for example `openid profile email offline_access`.
. *Add the refresh-token table.* Refresh tokens are kept in their own table, so existing `userSession` schemas don't change. Defining the table in your instance is what turns storage on:
+
[source,java]
----
qInstance.addTable(new UserSessionRefreshTokenMetaDataProducer(backendName).produce(qInstance));
----
+
For an RDBMS backend, create the table with columns matching `UserSessionRefreshToken`: `id`, `create_date`, `modify_date`, `session_uuid` (`VARCHAR(40)`, unique), `refresh_token` (`TEXT`), `refresh_token_expires_at` and `session_started_at`. For example (PostgreSQL):
+
[source,sql]
----
CREATE TABLE qqq_user_session_refresh_token
(
   id                       INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
   create_date              TIMESTAMP,
   modify_date              TIMESTAMP,
   session_uuid             VARCHAR(40) NOT NULL UNIQUE,
   refresh_token            TEXT,
   refresh_token_expires_at TIMESTAMP,
   session_started_at       TIMESTAMP
);
----
+
Name the table the same way your backend names the `userSession` table.
. *Set an encryption key.* Refresh tokens are stored encrypted, so the key is required whenever the table is defined and refresh tokens are enabled. Instance validation fails without it. See <<Encryption at rest>>.

Without the table, refresh tokens are discarded and sessions behave as they did before.

== Encryption at rest

A refresh token can mint new access tokens for as long as the provider allows (Authentik's default is 30 days). Anyone holding a copy of the table, such as a database dump, a replica or a backup in object storage, could impersonate its users. For that reason QQQ never stores a refresh token in plaintext:

* Each token is encrypted with AES-256-GCM, using a random 96-bit nonce per value. The stored value has the form `v1:<keyId>:<base64(nonce | ciphertext | tag)>`.
* The encryption is bound to the session: the session uuid and the `userSession` row's `userId` are the GCM associated data. A value copied to another row fails to decrypt.
* The key comes from configuration, never from the database. It is never serialized to clients or written to logs.
* A value that fails to decrypt (wrong or missing key, a tampered value, or a value moved from another row) is treated as having no refresh token. QQQ deletes the session's rows, the client gets the usual 401, and the user logs in again. The log entry records only the session uuid and a short reason, such as `authenticationFailed` or `unknownKeyId`.

=== Generating and setting the key

The key is 32 random bytes, base64-encoded:

[source,shell]
----
openssl rand -base64 32
----

Keep it in your secret store and pass it in through the environment. Don't commit it. `${env.X}` and `${prop.X}` references are resolved:

[source,java]
----
new OAuth2AuthenticationMetaData()
   // ...
   .withRefreshTokenEncryptionKey("${env.QQQ_OAUTH2_REFRESH_TOKEN_KEY}");
----

Every replica that shares the session tables must use the same key. If the key is lost, the stored refresh tokens can't be used: sessions end when their current access tokens expire, and users log in again.

=== Rotating the key

Each stored value records the id of the key that encrypted it. To rotate:

. Generate a new key.
. Make the new key current under a new id, and keep the old key, under its old id, in `previousRefreshTokenEncryptionKeys`. If you never set an id, the old key's id is `default`.
+
[source,java]
----
.withRefreshTokenEncryptionKey("${env.QQQ_OAUTH2_REFRESH_TOKEN_KEY_2026}")
.withRefreshTokenEncryptionKeyId("2026")
.withPreviousRefreshTokenEncryptionKeys(Map.of("default", "${env.QQQ_OAUTH2_REFRESH_TOKEN_KEY}"))
----
. Deploy. Previous keys are used only to decrypt. A value is re-encrypted with the current key the next time it is written, which happens on its session's next refresh.
. After the longest refresh-token lifetime has passed, remove the previous key. Any remaining values under that key can't be decrypted, so their sessions end as described above.

=== Local development

For local development only, `allowPlaintextRefreshTokens(true)` lets the instance validate without a key. Refresh tokens are then stored as-is, and validation logs a loud warning. Don't use it anywhere else. When a key is set, it is always used and this setting has no effect.

=== Table lock-down

`UserSessionRefreshTokenMetaDataProducer` hides the table, turns off auditing and hides the `refreshToken` field. It also sets the table's permission rules to `HAS_ACCESS_PERMISSION` on a dedicated permission, `qqq.internal.userSessionRefreshToken.noAccess.hasAccess`. Don't grant that permission to any role. Because the table is hidden, the permission isn't listed among the instance's available permissions. The v1 table API (query, get, count, export), reports and the UI therefore deny the table to every user, admins included. `OAuth2AuthenticationModule` reads and writes the table as the system user, which these rules don't affect.

If your app exposes tables through `qqq-middleware-api`, don't add API meta-data for this table. Its permission rules deny it there too.

Encrypting `userSession.accessToken` is not covered yet. Access tokens are shorter-lived, but they are still credentials, so keep database and backup access restricted.

== Meta-data options

These are set on `OAuth2AuthenticationMetaData`:

* `refreshTokensEnabled` - *Boolean, default true.* Store and use refresh tokens. Set it to `false` to keep the old behavior even when the table exists.
* `refreshTokenSkewSeconds` - *Integer, default 60.* QQQ refreshes the access token when it has this many seconds or fewer left, so requests don't fail at the exact moment of expiry. It must not be negative.
* `maxSessionLifetimeSeconds` - *Integer, optional.* The longest a session can be kept alive by refreshing, counted from login. After that, the refresh token is revoked and deleted, and the session ends when its current access token expires. If not set, there is no limit beyond the provider's own refresh-token lifetime.
* `refreshTokenTableName` - *String, optional.* Use a table other than `userSessionRefreshToken`. When set, the table must exist in the instance.
* `refreshTokenEncryptionKey` - *String, required when refresh tokens are stored.* A base64-encoded 32-byte AES key, or a `${env.X}` / `${prop.X}` reference to one. It is not serialized.
* `refreshTokenEncryptionKeyId` - *String, default `default`.* The id stored with each value encrypted under the current key. It may contain letters, digits, `_`, `.` and `-`, up to 64 characters.
* `previousRefreshTokenEncryptionKeys` - *Map of key id to key, optional.* Retired keys, used only to decrypt, for rotation. It is not serialized.
* `allowPlaintextRefreshTokens` - *Boolean, default false.* For local development only: lets refresh tokens be stored unencrypted when no key is set, and logs a warning.

== Behavior

* *When refreshes happen.* Resuming a session by its uuid (the session cookie) and `isSessionValid` both check the stored access token. If it has expired or is inside the skew window, QQQ calls the provider's token endpoint with `grant_type=refresh_token`. The endpoint comes from OIDC discovery on `baseUrl`. The new access token replaces the old one in `userSession`.
* *Rotation.* If the provider returns a new refresh token, QQQ saves it before the new access token. If the provider returns none, QQQ keeps using the existing one.
* *Concurrent requests.* Within one application process, requests for the same session are serialized, so only one of them calls the provider; the others use the token it stored. Across replicas, a replica whose refresh fails with `invalid_grant` first checks whether another replica already rotated the token, and if so uses that one.
* *Rejected refresh tokens.* When the provider answers `invalid_grant` (for example, the token expired or was revoked), QQQ deletes the session's `userSession` and refresh-token rows and removes it from the session store if one is enabled. The client gets the usual 401 and logs in again.
* *Temporary errors.* Network errors and other provider errors keep the refresh token, so a later request can try again. Meanwhile, the session is invalid once its access token has expired.
* *Logout.* Logging out deletes the stored refresh token. If the provider's discovery document advertises a `revocation_endpoint`, QQQ revokes the token there first (RFC 7009); revocation is best effort. Back-channel logout (see `BackChannelLogout.adoc`) deletes the refresh tokens of the sessions it ends, without calling the provider, since the provider already ended them.
* *Secrecy.* Refresh tokens stay on the server, encrypted (see <<Encryption at rest>>). They are not put on the `QSession`, in API responses or in cookies. The `refreshToken` field is hidden, so standard queries and gets leave it out. The table is hidden, not audited, and denied to every role. Log messages about refreshing, revoking and storing tokens never include the tokens, nor the descriptions in the provider's refresh error responses.

== Provider settings

* *Authentik:* in the OAuth2/OpenID provider, add the `offline_access` scope mapping to the provider's scopes. The access-token lifetime ("Access token validity") can then go back to a short value such as `minutes=5` or `hours=1`. "Refresh token validity" controls how long an idle session can last.
* *Auth0:* turn on *Allow Offline Access* in the API settings, and enable *Refresh Token Rotation* for the application. `Auth0AuthenticationModule` does not exchange authorization codes, so it doesn't use this feature; it applies to `OAuth2AuthenticationModule`.
* *Keycloak:* `offline_access` is a default optional client scope. Keycloak's `refresh_expires_in` response field is recorded, and refresh tokens past that time are not used.

== Subclasses

Subclasses that override `createSession` or `isSessionValid` and call `super` get refreshes without any changes, because refreshing happens in the access-token lookup that both methods use. A subclass that builds sessions without calling `super` (for example, for machine tokens) is not affected. Back-channel logout calls the public static method `OAuth2AuthenticationModule.deleteStoredRefreshTokens(QInstance, Collection<String>)`, which is also available to custom logout flows.
